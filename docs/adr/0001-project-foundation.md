# 独立 Alpha 扫描项目基础架构

日期：2026-11-05。状态：方案建议，待实施阶段验证；不是已完成的代码变更。

## 背景

需要一个可以解释和回放的二段扫描系统。现有候选在采集、标注或形态计算上各有价值，但尚未发现一个经本次验证、可以直接覆盖 Alpha 二段实时研究全流程的成品。

## 决定与依据

1. 新建独立仓库，选择性移植 MIT 底本的基础模块，记录来源和版权。核心二段引擎自行实现，避免继承已发现的时间语义问题。
2. Alpha 是首版必达数据源。普通 Binance 历史数据可帮助验证基础模块，但不替代 Alpha 的产品验收。
3. 使用 TypeScript 单体应用和 SQLite。纯规则不依赖 HTTP、数据库、UI、当前系统时钟或随机数；运行时由外部传入显式时刻。
4. 原始响应、规范数据版本、状态决策、人工标签和结果统计分别保存；以不可变证据重建可变视图。
5. 首版采用规则 v0，VCP 是后续独立对照实验。先证明数据和时间语义正确，再评估参数和因子。
6. 按用户要求排除 HertzFlow，暂缓 Freqtrade。自动交易和外部通知不进入本轮工作包。

## 取舍

按模块移植需要重新建立入口和数据契约，但能避免把 Turso、Telegram 和事后检测逻辑一起带入新项目。SQLite 简化单用户运行，代价是首版不支持多写入节点；未来确有多用户或容量需求时另立决策。

自建状态机意味着策略本身仍需验证。上游项目的星数、测试数量和许可均不能替代本项目的样本外证据。

## 重新评估的触发条件

- Alpha API 在目标环境不可用或历史覆盖不足：先调整数据范围与采样方式，记录限制；不得悄悄把现货样本包装成 Alpha 结果。
- 底本模块无法独立通过测试，或移植引入大量无关依赖：缩小复用范围，保留源码审计和来源记录。
- 50 个交易对的单进程试运行无法满足延迟指标：先分析网络预算、存储写入和队列积压，再决定是否增加 WebSocket。
- 产品明确转向交易执行、多用户或新市场：更新范围与 ADR，不通过新增可选配置暗中扩大首版。
